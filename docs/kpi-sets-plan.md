## 1. บริบท / ที่มา

owner (2026-07-21): *"กำลังจะแยกตัวชี้วัด มีจัดประเภทตัวชี้วัด — ตรวจราชการเขต 3 / งานคุณภาพ (HA) / ร่วม อบจ. / จังหวัด (Ranking) / Smart Hospital · ข้อมูลตัวชี้วัดที่เรากรอกเข้ามาต้องเอามาจัดประเภทอีก · หมวดหมู่ในระบบตอนนี้เป็นเหมือนข้อมูลเชิงลึกของ HDC"*

**ข้อสังเกตของ owner ถูกต้อง** — หมวดหมู่ปัจจุบันคือเมนู HDC จริงๆ (breadcrumb ทางการ) ซึ่งเป็นแกน "เรื่องอะไร" ที่ยังใช้ได้ แต่ครอบไม่ถึงตัวชี้วัดนอก HDC — ตรงกับที่ [`kpi-work-groups-plan.md` §1](kpi-work-groups-plan.md) ทำนายไว้ล่วงหน้าแล้วว่า *"หมวดหมู่ HDC ใช้ได้เฉพาะ KPI ที่มาจาก HDC"*

### ข้อสรุป: ไม่รื้อของเดิม — เพิ่มแกนที่ 3

| | หมวดหมู่ HDC *(มีแล้ว)* | กลุ่มงาน *(มีแล้ว)* | **ชุดตัวชี้วัด** *(ไฟล์นี้)* |
|---|---|---|---|
| ตอบคำถาม | ตัวชี้วัดนี้**เรื่องอะไร** | **ใครใน รพ.** รับผิดชอบ | **ส่งใคร / พันธะไหน** |
| ตัวอย่าง | ส่งเสริมป้องกัน › การคัดกรอง | ปฐมภูมิ | ตรวจราชการ เขต 3 |
| มาจากไหน | เมนู HDC (มีหลักฐาน) | ผังองค์กร รพ. | เอกสารข้อตกลง/คำรับรองแต่ละชุด |
| ความสัมพันธ์ | 1 KPI = 1 หมวด | 1 KPI = หลายกลุ่ม | **1 KPI = หลายชุด** |
| เปลี่ยนตามปีงบ | ไม่ | ไม่ | **ใช่ — ชุดเปลี่ยนทุกปี** |
| เก็บที่ | `kpi_reports.category` | `kpi_work_groups` | ตารางใหม่ `kpi_set_items` |

**ทำไมต้องเป็นแกนแยก ไม่ใช่ยัดลงหมวดหมู่:** ตัวเดียวกันอยู่ได้หลายชุดพร้อมกัน (เช่น "คัดกรอง DM/HT 35+" น่าจะอยู่ทั้งตรวจราชการและ Ranking จังหวัด) — หมวดหมู่เป็น 1:1 ถ้ายัดลงไปต้องเลือกชุดเดียวหรือสร้าง KPI ซ้ำ ทั้งสองทางผิดทั้งคู่

### ⚠️ กับดักที่ต้องกันตั้งแต่แรก — "แกนยุบรวมกัน" (axis collapse)

ตอนนี้ owner สร้างหมวดหมู่เองได้ (self-service) → มีโอกาสสูงที่จะเผลอสร้าง**หมวดหมู่**ชื่อ `ตัวชี้วัดงานคุณภาพ (HA)` ขึ้นมาแก้ขัดก่อนที่ฟีเจอร์นี้จะเสร็จ

**ห้ามทำ** — ถ้าทำ 2 แกนจะทับกัน, dashboard นับซ้ำ, และตัวที่อยู่ 2 ชุดจะกลับไปติดปัญหา 1:1 เดิม
**กติกา:** ชื่อหมวดหมู่ = *เรื่องอะไร* (การคัดกรอง, งานโภชนาการ, คุณภาพบริการ) · ชื่อชุด = *ส่งใคร* (ตรวจราชการ, HA, อบจ.)

## 3. ⛔ สิ่งที่ต้องได้จาก owner (blocker — เดาแทนไม่ได้)

ตรงตามกฎ CLAUDE.md ข้อ 5 (ห้ามเดา mapping) — ผมเดาแทนไม่ได้เลยว่า KPI ตัวไหนอยู่ชุดไหน

### 3.1 รายชื่อตัวชี้วัดของแต่ละชุด
ต่อ 1 ชุด ขอ: **รายชื่อตัวชี้วัด + เลขข้อ (ถ้ามี)** จากเอกสารต้นทาง (คำรับรอง/คู่มือตรวจราชการ/เกณฑ์ HA ฯลฯ)

จากนั้นแยกเป็น 2 กอง:
- **กอง A — ตรงกับ 39 ตัวที่มีอยู่แล้ว** → แค่ติ๊กชุด (งานคลิก ไม่ต้องเขียนโค้ด)
- **กอง B — ยังไม่มีในระบบ** → ต้องสร้าง KPI ใหม่ ส่วนใหญ่จะเป็น manual key-in (ระบบพร้อมแล้ว — ดู §5)

### 3.2 ชุดผูกปีงบไหม
`ตรวจราชการ เขต 3` เปลี่ยนรายการทุกปี → เก็บชื่อชุดเป็น `ตรวจราชการ เขต 3` เฉยๆ แล้วมีคอลัมน์ `fiscal_year` แยก **หรือ** ใส่ปีในชื่อไปเลย (`ตรวจราชการ เขต 3 ปี 2569`)
- **แนะนำ:** มีคอลัมน์ `fiscal_year` แยก (ปีหน้าลอกชุดเดิม → แก้รายการ → ไม่เสียประวัติปีนี้)

### 3.3 ต้องเก็บ "เลขข้อ" ในชุดไหม
เช่น ตรวจราชการเรียกตัวนี้ว่า "ข้อ 1.5" แต่ Ranking เรียก "ตัวชี้วัดที่ 12" → เลขข้อเป็นของ**ความสัมพันธ์ KPI↔ชุด** ไม่ใช่ของ KPI
- **แนะนำ:** มีคอลัมน์ `set_code` (nullable) — ไม่ใช้ก็ปล่อยว่าง ต้นทุนเกือบศูนย์ แต่ถ้าไม่ทำตอนนี้แล้วมาเพิ่มทีหลังต้องมา ALTER + แก้ UI

### 3.4 Ranking มี "น้ำหนักคะแนน" ไหม — ✅ **ยืนยันแล้ว: มี (และซับซ้อนกว่าน้ำหนักเดี่ยว)**
owner ส่ง `docs/data_owner/คะแนน Ranking 2569.xlsx` (21 ก.ค.) → **มีน้ำหนักจริง + เกณฑ์คะแนน 1-5** ดู §15 · ยังไม่ทำตอนนี้ (เฟสท้ายๆ หลัง L) เพิ่มคอลัมน์ทีหลังได้ ไม่กระทบข้อมูลเดิม

## 4. Schema ที่เสนอ

```sql
-- 1) ตารางชุดตัวชี้วัด (lookup — จัดการเองผ่าน /admin เหมือน categories/work_groups)
CREATE TABLE kpi_sets (
  id          INT AUTO_INCREMENT PRIMARY KEY,
  name        VARCHAR(150) NOT NULL,          -- 'ตัวชี้วัดตรวจราชการ เขต 3'
  slug        VARCHAR(50)  NOT NULL,          -- 'inspection-r3' → URL /sets/inspection-r3
  fiscal_year SMALLINT     NULL,              -- 2569 (NULL = ใช้ทุกปี เช่น Smart Hospital)
  description TEXT         NULL,
  sort_order  INT DEFAULT 0,
  created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_set_name (name),
  UNIQUE KEY uk_set_slug (slug)
) ENGINE=InnoDB CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 2) junction: 1 KPI ↔ หลายชุด (+ ข้อมูลที่เป็นของ "ความสัมพันธ์" ไม่ใช่ของ KPI)
CREATE TABLE kpi_set_items (
  kpi_id     VARCHAR(50) NOT NULL,
  set_id     INT         NOT NULL,
  set_code   VARCHAR(20) NULL,                -- เลขข้อในชุดนั้น เช่น '1.5' (ดู §3.3)
  sort_order INT DEFAULT 0,
  PRIMARY KEY (kpi_id, set_id),
  KEY idx_ksi_set (set_id),                   -- เร่ง query "KPI ของชุดนี้"
  CONSTRAINT fk_ksi_kpi FOREIGN KEY (kpi_id) REFERENCES kpi_reports(id) ON DELETE CASCADE,
  CONSTRAINT fk_ksi_set FOREIGN KEY (set_id) REFERENCES kpi_sets(id)   ON DELETE CASCADE
) ENGINE=InnoDB CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

### ทำไม FK → `id` (ต่างจาก work_groups ที่ FK → `name`)

`kpi_work_groups` เลือก FK อ้าง `name` เพราะ `users.department` เป็น string ที่ฝังอยู่ใน JWT/auth — เปลี่ยนเป็น id จะต้องรื้อ auth (ดู [`kpi-work-groups-plan.md` §4](kpi-work-groups-plan.md))

**ชุดตัวชี้วัดไม่มีข้อจำกัดนั้นเลย** (ไม่มีอะไรใน auth อ้างถึง) + มีเหตุผลบวก 2 ข้อ:
1. ชื่อชุดยาวและมีโอกาสแก้สูง (`ตรวจราชการ เขต 3` → `ตรวจราชการ เขตสุขภาพที่ 3`) — FK→id ทำให้ rename ฟรี ไม่ต้องพึ่ง CASCADE
2. ต้องมี `slug` สำหรับ URL อยู่แล้ว → มี surrogate key อยู่ดี

⚠️ ผลที่ตามมา: `attachSets` ต้อง JOIN (ไม่เหมือน `attachWorkGroups` ที่อ่านชื่อตรงๆ) — ต้นทุนไม่มีนัยที่ขนาดข้อมูลจริง

## 5. สิ่งที่ระบบ **มีอยู่แล้ว** (ไม่ต้องสร้างใหม่)

ตัวชี้วัดชุดใหม่ส่วนใหญ่ (HA / Smart Hospital / อบจ.) จะไม่ได้มาจาก HDC → ต้องกรอกเอง — ตรงนี้งาน Phase H-J ที่เพิ่งเสร็จ (19-20 ก.ค.) รองรับครบแล้ว:

| ต้องการ | สถานะ |
|---|---|
| KPI กรอกเอง ไม่ให้ cron ไปดึงทับ | ✅ `manual_entry` (batch/cron ข้ามให้เอง) |
| กรอกค่าเดียว (ไม่แยกราย รพ.สต.) | ✅ `manual_scope='single'` + `POST /api/monthly/single` |
| กรอกราย รพ.สต. 7 หน่วย | ✅ `manual_scope='unit'` + `POST /api/monthly/detail` |
| ระบุแหล่งข้อมูลที่ไม่ใช่ HDC | ✅ `data_source` (แก้ในฟอร์ม `/admin` + badge ในตาราง) |
| staff เจ้าของกลุ่มงานกรอกเอง + ล็อกเดือน | ✅ Phase H1-J (`lib/kpiOwnership.ts`) |
| audit ใครกรอก/เมื่อไหร่ + กันกรอกทับ | ✅ `data_change_log` + ล็อกฟอร์มหลังบันทึก |
| สร้าง KPI ใหม่เองผ่านเว็บ | ✅ KpiWizard |

→ **กอง B (KPI ใหม่) แทบไม่ต้องเขียนโค้ดเพิ่มเลย** เหลือแค่ owner สร้างผ่านหน้าเว็บ + ติ๊กชุด

⚠️ **ข้อเดียวที่ติด:** `kpi_reports.category` เป็น `NOT NULL` และ dropdown มีแต่หมวด HDC → KPI นอก HDC ก็**ต้อง**เลือกหมวด → owner ต้องสร้างหมวดหมู่เชิงเนื้อหาใหม่เอง (เช่น กลุ่มหลัก `คุณภาพและความปลอดภัย` › หมวดย่อย `มาตรฐาน HA`) **ห้ามตั้งชื่อหมวดซ้ำกับชื่อชุด** (§1 axis collapse)

> 📌 **K1-K6 คือ "แกนชุด" อย่างเดียว — ยังไม่พอสำหรับชุดตรวจราชการ** · หลังตรวจไฟล์จริง (§10) ต้องมีอีกชุดงาน **L1-L5 (รองรับตัวชี้วัดแบบรายงาน)** ดู §11 · ลำดับที่แนะนำอยู่ท้าย §11

### ทำไมไม่แยกหน้าจริง 5 หน้า (K6)
1. **5 ชุดวันนี้ ปีหน้าเป็น 8** (ตรวจราชการ 2570, PA ผู้ตรวจ, HA re-accredit…) → แยกหน้าจริง = เพิ่มชุดทีต้องเรียก dev ทุกครั้ง = ตายแนวทาง self-service ที่ยึดมาทั้งโปรเจกต์
2. เนื้อในทั้ง 5 หน้าคือ**ตารางเดียวกันคนละฟิลเตอร์** → copy 5 รอบ = แก้บั๊ก 5 ที่
3. `/sets/[slug]` แบบ dynamic ให้ผลลัพธ์ที่ owner อยากได้ (เปิดมาเห็นเฉพาะชุดนั้น + สรุปผ่าน/ไม่ผ่าน) โดยเพิ่มชุดใหม่แล้วหน้าเกิดเอง

## 8. ผลดี / ผลเสีย

### ✅ ผลดี
1. **ตอบโจทย์ตรงตัว** — เปิดมาเห็น "ตรวจราชการผ่านกี่ตัว" ซึ่งเป็นภาษาที่ผู้บริหารใช้จริง
2. **many-to-many ตรงความจริง** — ตัวเดียวส่งหลายที่ได้ ไม่ต้องสร้าง KPI ซ้ำ (ซ้ำ = ข้อมูลรายเดือนแตกเป็น 2 ชุด = หายนะ)
3. **ไม่รื้อของเดิม** — หมวดหมู่ HDC + กลุ่มงาน ที่ verify ผ่านแล้วไม่ถูกแตะ
4. **self-service ต่อ** — owner เพิ่ม/แก้ชุดเองได้ ไม่ต้องรอ dev (แนวทางเดียวกับ categories/work_groups)
5. **ต่อยอด redesign ได้** — แกนนี้เหมาะเป็นเมนูระดับบนของหน้าเว็บใหม่ ("หน้าเว็บเหมือนหลังบ้าน" คือโจทย์ที่ยังค้าง)
6. **รับมือ KPI โต 39 → 100+** — พอตัวชี้วัดเยอะ list เดียวจะใช้ไม่ไหว ต้องมีแกนนำทางระดับบนอยู่ดี
7. **ความเสี่ยงต่ำ** — ไม่แตะ engine/เป้าหมาย/auth เลย (ต่างจาก work groups ที่ยังต้องแตะ `users`)

### ❌ ผลเสีย / ต้นทุน
1. **mapping ต้องกรอกมือ** — ผมเดาแทนไม่ได้ (กฎ CLAUDE.md ข้อ 5) — เป็นแรงงานคนล้วน เหมือน work groups
2. **แกนที่ 3 = ภาระความเข้าใจ** — ต้องอธิบาย staff ว่าหมวดหมู่ ≠ กลุ่มงาน ≠ ชุด (แก้ด้วย label/tooltip ในหน้าเว็บ)
3. **KPI นอก HDC ต้องมีหมวดหมู่ด้วย** (`category NOT NULL`) → owner ต้องสร้างหมวดเชิงเนื้อหาเพิ่ม (§5)
4. **`/admin` ยาวขึ้นอีก** — ~1550 บรรทัด + อีก 2 ส่วน → PLAN.md §F (แยกไฟล์ต่อแท็บ) เริ่มคุ้มแล้วจริงๆ
5. **go-live เพิ่มเป็น 6 ตาราง** — checklist ยาวขึ้น (แต่ `/api/init` idempotent อยู่แล้ว)
6. **ถ้าภายหลังเป้าต่างกันตามชุดจริง → ต้องรื้อ** (ยืนบนคำตอบ §2 ข้อ 2) — จุดรื้อคือย้าย target ลง `kpi_set_items` + แก้ `/admin/targets` + การประเมินสถานะ

## 9. สรุป

**สิ่งที่จะทำ:** เพิ่ม 2 ตาราง (`kpi_sets` + junction `kpi_set_items`) เป็น**แกนที่ 3** ของการจัดตัวชี้วัด แล้วต่อฟิลเตอร์ + หน้า `/sets/[slug]` แบบ dynamic — **ไม่แยกหน้าจริงต่อประเภท**

**ทำไมไม่รื้อหมวดหมู่เดิม:** หมวดหมู่ HDC ตอบคำถาม "เรื่องอะไร" ซึ่งยังถูกและมีหลักฐานยืนยัน (breadcrumb HDC) · ชุดตัวชี้วัดตอบ "ส่งใคร" · สองอย่างนี้เป็นอิสระต่อกัน ยุบรวมเมื่อไหร่พังทันทีเพราะ 1 KPI อยู่หลายชุดได้แต่อยู่หมวดเดียว

**ต้นทุนจริงไม่ใช่โค้ด แต่คือข้อมูล** — เหมือน work groups เป๊ะ: โค้ด ~5 phase ทำได้เร็ว แต่ "KPI ตัวไหนอยู่ชุดไหน" ต้องรอ owner ให้รายการจากเอกสารต้นทาง (§3.1)

**blocker ที่ต้องเคลียร์ก่อนเริ่ม K1:** §3.1 (รายชื่อต่อชุด) · §3.2 (ปีงบ) · §3.3 (เลขข้อ)

### 11.1 Schema ที่ต้องเพิ่ม

```sql
-- (1) ชนิดการวัด — บอกว่า KPI ตัวนี้วัดเป็นตัวเลขหรือเป็นข้อความ/ระดับ
ALTER TABLE kpi_reports
  ADD COLUMN measure_type VARCHAR(10) NOT NULL DEFAULT 'numeric',  -- 'numeric' | 'text'
  ADD COLUMN report_freq  VARCHAR(10) NOT NULL DEFAULT 'monthly';  -- 'monthly' | 'quarterly' | 'yearly'

-- (2) ผลงานที่เป็นข้อความ (คู่กับ value เดิม — ไม่แตะคอลัมน์เดิม)
ALTER TABLE monthly_data
  ADD COLUMN value_text VARCHAR(255) NULL;   -- ใช้เมื่อ measure_type='text'
-- ⚠️ value ยังเป็น NOT NULL → KPI แบบ text เขียน value=0 แล้วให้ evaluateKpiStatus
--    คืนสถานะพิเศษ 'narrative' (ไม่ตัดสินผ่าน/ไม่ผ่าน) — เลี่ยงการทำ value เป็น NULL
--    ซึ่งจะกระทบ scorecard/export/drilldown ทุกจุดที่อ่าน value

-- (3) เป้าหมายที่เป็นข้อความ + เป้าอ้างอิงระดับเขต/จังหวัด
--     เก็บที่ junction เพราะเป็นของ "ชุดนี้" ไม่ใช่ของ KPI (ชุดอื่นอาจไม่มี)
ALTER TABLE kpi_set_items
  ADD COLUMN target_text     VARCHAR(100) NULL,  -- เป้า รพ. แบบข้อความ เช่น '≥ ร้อยละ 95'
  ADD COLUMN target_region   VARCHAR(100) NULL,  -- เป้าเขต (อ้างอิง ไม่ใช้ตัดสิน)
  ADD COLUMN target_province VARCHAR(100) NULL;  -- เป้าจังหวัด (อ้างอิง)

-- (4) บันทึกเชิงคุณภาพต่อรอบ — ตารางใหม่ (แยกจาก monthly_data เพื่อให้ cron ไม่มีวันทับ)
CREATE TABLE kpi_period_notes (
  kpi_id      VARCHAR(50) NOT NULL,
  period      VARCHAR(7)  NOT NULL,          -- 'YYYY-MM' (ไตรมาส = เดือนสุดท้ายของไตรมาส)
  problem     TEXT NULL,                     -- ปัญหาอุปสรรค
  next_action TEXT NULL,                     -- แนวทางการดำเนินงานต่อไป
  data_ref    VARCHAR(500) NULL,             -- แหล่งที่มาข้อมูล (link/ช่องทาง)
  updated_by  VARCHAR(255) NULL,
  updated_at  TIMESTAMP NULL DEFAULT NULL,
  PRIMARY KEY (kpi_id, period),
  CONSTRAINT fk_kpn_kpi FOREIGN KEY (kpi_id) REFERENCES kpi_reports(id) ON DELETE CASCADE
) ENGINE=InnoDB CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

**สิ่งที่ตั้งใจ *ไม่* ทำ (ตัดสินจากข้อมูลจริง):**

## 15. 🔍 ผลตรวจไฟล์ Ranking — `คะแนน Ranking 2569.xlsx` (21 ก.ค. 2569)

19 ชีต (สรุป · รายละเอียด · ปรับรายละเอียด · แบบฟอร์ม + ราย กลุ่มงาน สสจ. 15 ชีต) — ชีต **"สรุป"** คือตัวหลักที่อ่านได้ครบ

### 15.1 โครงสร้างคะแนน — มี "น้ำหนัก" + "เกณฑ์คะแนน 1-5" (2 ชั้น)
- **44 ตัวชี้วัด · น้ำหนักรวม = 100 คะแนนพอดี** (น้ำหนัก 3 = 18 ตัว, น้ำหนัก 2 = 23 ตัว, ข้อย่อยไม่มีน้ำหนัก 3)
- **ไม่ใช่แค่ผ่าน/ไม่ผ่าน × น้ำหนัก** — แต่ละตัวมี **เกณฑ์ให้คะแนน 1-5 ตามช่วงที่ทำได้** (คอลัมน์ H-L ในชีตรายละเอียด = 5 ช่วง)
  - ตัวอย่าง MMR2 (น้ำหนัก 3): ≤90%→1 · 92%→2 · 95%→3 · 98%→4 · 100%→5 · ทำได้ 95% = 3 คะแนน × น้ำหนัก 3 = 9 แต้ม
- รวมทุกตัว → **จัดอันดับ รพ. ในจังหวัด**
- คอลัมน์เพิ่ม: **หน่วยประเมิน** (สสอ./รพ.S/M2/F2/F3/รพ.สต. — mark 1 ว่าตัวไหนใช้กับหน่วยชนิดใด) · **แหล่งข้อมูล** (หลายตัว = HDC) · **กลุ่มงานรับผิดชอบ** (ชื่อของ สสจ.: อวล./คบ./ยุทธฯ — ไม่ตรงกลุ่มงาน รพ. เรา ต้อง map อีกชั้น)

### 15.2 ผลต่อ schema (เฟสท้ายๆ หลัง L — ยังไม่ทำ)
Ranking เป็นชุดที่**ซับซ้อนที่สุดใน 5 ชุด** — ต้องเพิ่มบน `kpi_set_items` (nullable ทั้งหมด ชุดอื่นไม่ใช้):
```sql
ALTER TABLE kpi_set_items ADD COLUMN weight TINYINT NULL;          -- น้ำหนัก 2/3
-- เกณฑ์คะแนน 5 ช่วง: เก็บเป็น JSON ต่อ (kpi,set) เช่น [{"min":95,"score":3}, ...]
ALTER TABLE kpi_set_items ADD COLUMN score_bands TEXT NULL;
```
+ engine แปลง %→คะแนน 1-5→× น้ำหนัก→รวมอันดับ (เป็น evaluation model ที่ 3 ต่างจาก target-% และ pass/fail) · **ทำตอนสร้างชุด Ranking จริง ไม่ใช่ตอนนี้**

### 15.3 ซ้ำกับตัวชี้วัดที่มีอยู่
หลายตัวดึงจาก HDC ที่ทำไว้แล้วได้ (ไฟล์ระบุ "แหล่งข้อมูล=HDC" ตรงกัน): ANC ≤12 สัปดาห์, คัดกรองพัฒนาการ (DSPM), ผู้สูงอายุ 9 ด้าน, วัคซีน 2 ปี/MMR2, แพทย์แผนไทย, ยาสมุนไพร ฯลฯ — จับคู่จริงตอน L5 (ชุด Ranking)

> **สรุป blocker:** ไม่มีอะไรใหม่บล็อก K1-K3 · Ranking กระทบเฉพาะเฟสสร้างชุด Ranking (ปลายทาง) · ข้อมูล 2 ไฟล์ (ตรวจราชการ + Ranking) ครบพอสำหรับออกแบบ L1/L3/L5 แล้ว

- เกณฑ์ 5 ช่วง = "ระดับ 5 ขั้น" ที่แต่ละขั้น = คะแนน (ต่อยอดจาก level ที่มี L1b)
